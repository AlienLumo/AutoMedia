# 资讯池 · 信息源注册与每小时轮询

> 定位：把「泛 AI / 商业股市 / 创业访谈 / 科技数码 / 创客 / 娱乐明星」的上游信息源做成**可每小时轮询的注册表**，新条目自动落进资讯池，供后续与 B站 826 号池做「上游→下游」对照。
> 数据目录：`1AMdata/news/`（代码与数据同目录，自包含，不改动两套采集管线）。
>
> 本仓库中的对应位置：源注册表见 `news-source/config/sources.tsv`，示例素材见 `news-source/examples/261111/`。

## 一、目录

```
1AMdata/news/
  sources.tsv            281 个源（人工维护的唯一真源）
  news_watch.py          轮询器（--validate / --once / --stats）
  run_hourly.ps1         常驻每小时循环（推荐）
  run_once.ps1           单次执行（给计划任务用）
  source_status.json     源体检结果（--validate 产出）
  state.json             已见条目 + 每源状态（去重依据）
  pool/items.jsonl       资讯池（append-only，永久累积）
  runs/YYYYMMDD-HHMMSS.json   每轮审计（新增数/失败源/耗时）
  digests/YYYY-MM-DD.md  当日摘要（按 P0–P3 分层）
  logs/                  运行日志
```

## 二、一手性判定：平台无关，看「谁是第一发布者」

> 结论先说：**小红书、公众号完全可能是 P0 一手**。判定标准不是平台，而是「该主体是不是这条信息的最初发布者」。

| 层级 | 定义 | 例子 |
|---|---|---|
| **P0 原始发布** | 事件当事人、官方机构、原始文件/数据 | 公司官网/官方公众号/官微发布、政府公告、交易所公告（巨潮/披露易）、财报电话会、论文原文、产品 release notes、官方 GitHub release |
| **P1 首发报道** | 有编辑核实、首发于该媒体 | 财新/晚点/界面/第一财经/Reuters/Bloomberg/The Information 的首发稿 |
| **P2 转述编译** | 引用 P0/P1 的二次加工 | 机器之心/量子位转外媒、KOL 编译、券商研报转述 |
| **P3 聚合搬运** | 无溯源、热搜榜、搬运号 | 微博热搜、抖音热点、营销号、无出处短视频 |

**平台中性原则（回答「小红书/公众号是不是一手」）：**

| 平台 | 可能是 P0 的情形 | 通常是 P2/P3 的情形 |
|---|---|---|
| 微信公众号 | **公司/机构/政府的官方号**（DeepSeek、月之暗面、智谱、各地政府发布、协会）→ 很多国内公司**只发公众号不发官网**，公众号就是唯一一手渠道 | 个人 KOL 的「解读」「搬运」 |
| 小红书 | **品牌官方号、开发者/当事人本人首发**（首发实测、产品泄露、现场照片） | 种草号、二传截图 |
| 微博 | 官方账号、当事人本人、工作室声明 | 热搜榜、营销号转发 |
| 知乎 | **当事人回答**、官方机构号 | 转载/汇总回答 |
| B站/抖音 | 创作者**本人原创首发**（自己做的项目/实测） | 搬运、切片、二创解读 |

**给源打标签的三个字段**：`level`（P0–P3）、`subject`（官方/当事人/媒体/数据机构/聚合/平台）、`note`（为什么是这个级别）。后续如果要做「首发时间竞赛」，还需要在条目层记录 `published` 并与 B站 跟进时间比对——这正是 `items.jsonl` 里保留 `published` 的原因。

## 三、源注册表（sources.tsv）

字段：

| 字段 | 说明 |
|---|---|
| `id` | 唯一编号，如 `s001` |
| `name` | 源名称 |
| `region` | 中 / 外 |
| `cat` | 分类：AI官方 / 论文 / 外媒 / 财经股市 / 创投 / 访谈 / 科技数码 / 供应链数据 / 创客 / 娱乐明星 / 国内媒体 / 国内官方 / 国内数据 / 国内平台 / 平台 |
| `level` | P0 / P1 / P2 / P3 |
| `subject` | 官方 / 当事人 / 媒体 / 数据机构 / 聚合 / 平台 |
| `adapter` | `rss` / `json` / `html` / `manual` |
| `url` | 主页（人看的地址） |
| `feed` | 机器抓取地址（RSS/Atom/API）；空 = 暂不可自动抓 |
| `enabled` | 1 = 参与每小时轮询；0 = 暂不（等补 feed 或人工处理） |
| `note` | 备注 |

覆盖情况：**281 个源**（中 128 / 外 153；P0 101 / P1 133 / P2 24 / P3 23）。其中 **135 个已启用自动轮询**（rss 84 + html 50 + json 1），其余 104 个为 `manual`（公众号/小红书/付费墙/需要登录/无 feed），保留在注册表里以便后续补链或人工巡检。首轮实测：135 源抓取 2,374 条（P0 724 / P1 1,354 / P2 207 / P3 89），第二轮只新增 4 条，去重正常。

## 四、运行方式

```powershell
# 1) 先体检（看哪些 feed 活着）
python 1AMdata/news/news_watch.py --validate

# 2) 跑一轮（首次建议 --max-age-days 7，避免灌入太多历史）
python 1AMdata/news/news_watch.py --once --max-age-days 7

# 3) 看池子统计
python 1AMdata/news/news_watch.py --stats
```

**每小时常驻**（推荐，避免 Windows 计划任务 5 天期限问题）：

```powershell
powershell -ExecutionPolicy Bypass -File 1AMdata/news/run_hourly.ps1
```

或注册计划任务（需管理员权限，注意你之前踩过「5 天期限无法延长」的坑）：

```powershell
schtasks /Create /TN "NewsWatchHourly" /TR "powershell -ExecutionPolicy Bypass -File <项目根>\1AMdata\news\run_once.ps1" /SC HOURLY /MO 1
```

**限速纪律**：单并发、每源间隔 1.2s、超时 12s、失败重试 2 次；一轮约 6–10 分钟（126 个源）。不做登录、不绕验证码、只读抓取。

## 五、增量与去重

- 去重键：`sha1(link|title)`，另维护 `link` 索引；`state.json` 存最近 30 天已见，跨源同一新闻只入池一次（后到的源不重复入池）。
- 首次运行用 `--max-age-days` 限制回溯天数（默认 14 天）。
- 新条目字段：`ts / source / src_id / region / cat / level / subject / title / link / published / summary / run`。
- 当日摘要写 `digests/YYYY-MM-DD.md`，按 P0–P3 分层，便于每天先看 P0。

## 六、平台限制（要如实说明）

| 平台 | 能否自动抓 | 现实做法 |
|---|---|---|
| 公众号 | ❌ 无公开接口 | ① 优先抓该机构的官网/微博/知乎镜像；② 自建 RSSHub（`/wechat/...` 路由，需要微信读书/公众号后台）或 wechat2rss；③ 关键官方号人工每日巡检 |
| 小红书 | ❌ 无公开 API | 只能登录态浏览器半自动（每日 1–2 次，别高频）——已有 `social-operator` 能力可复用 |
| 微博 | ⚠️ 需登录/API 申请 | RSSHub `/weibo/user/{uid}`（自建），或只抓热搜（P3） |
| 抖音 | ❌ | 已有 `douyin-auto` 浏览器方案，低频 |
| 付费墙（The Information/Bloomberg/WSJ/FT） | ⚠️ 只有标题+摘要 | 只做标题级监控，避免版权问题 |

## 七、与 B站 池的联动（下一步）

```
上游源（news/pool） → 关键词/实体提取 → 与 B站 watch 新视频匹配
    → 产出「谁先跟、跟了多久、讲了什么」的对照表
```

建议把 `news_watch.py` 的输出与 `1AMdata/watch/inbox.jsonl`（B站新视频）按实体（公司名/产品名/模型名）做匹配，形成每日「上游-下游」对照。

## 八、维护

- 加源：直接编辑 `sources.tsv`（保持表头），填 `feed` 后把 `enabled=1`。
- 体检：每周跑一次 `--validate`，失败源看 `source_status.json`。
- 失效处理：feed 变更只改 `feed` 列；连续失败 3 轮的源在 `state.json` 里会体现，建议手动确认。

## 九、每日 17:00 飞书推送

- **脚本**：`daily_report.py` —— 取近 24h 池子，按四维度分析：
  - **行业动向**（技术/产业主线）
  - **股市投资**（资金/公司面）
  - **创业前瞻**（新公司/新模式）
  - **自媒体**（内容/流量侧）
- **每维度输出**：Top 5 精选（带链接）、动作信号条数、子话题分布（如 大模型 / 芯片算力 / 机器人）、一句观察。
- **少说规则**：某维度 0 条 → 写「今日无明显信号（略）」；<3 条 → 略述；其余省略。
- **推送**：复用 `bilibili-auto/scripts/feishu_push.py`（飞书应用模式，现有凭证）。
- **定时**：Windows 计划任务 `NewsDaily1700`，每天 17:00 执行 `run_daily.ps1`。
- **产物**：报告 `reports/YYYY-MM-DD-daily.md`；日志 `logs/daily.log`。
- **手动**：

```powershell
python 1AMdata/news/daily_report.py --push           # 生成并推送
python 1AMdata/news/daily_report.py --push --dry-run # 演练
schtasks /Run /TN "NewsDaily1700"                    # 立即触发一次
```

## 十、信息源引擎（LLM 版，17:00 主推送）

- **脚本**：`info_engine.py`（已替换 `run_daily.ps1` 的调用；`daily_report.py` 保留作规则回退）。
- **一条合并消息**（精选 + 文章合并为单条，超长按 4,500 字/条自动切分）：
  1. **今日精选**：从近 24h 池子里按「影响力/劲爆度」挑 8–10 条（摘要 + 链接 + 30 字批注），只推精选，不推全量。
  2. **今日全球总结文章**：LLM 写 900–1300 字分析文章，有主见、性格鲜明、有理有据，结合 24h 微观 / 1–3 个月中期 / 3–5 年长期趋势；**风格与结构按日期哈希轮换**（投行晨报 / 科技评论 / 学术综述 / 财经专栏 / 一线纪要 / 布道者 × 主线叙事 / 三段论 / 对抗式 / 时间轴 / 清单体 / 单点深挖），避免八股。
  - 消息结构：`【信息源引擎】YYYY-MM-DD · 精选 + 全球总结` → `━━ 今日精选 ━━`（编号列表）→ `━━ 今日全球总结 ━━`（标题 + 正文）。
- **LLM**：本地 DSH 的 newapi 网关（`<USER_HOME>\.dsh\.credentials.yaml` 的 `NEWAPI_API_KEY`，模型 `gpt-6.1-sol`），经 `curl.exe` 调用（带浏览器 UA 过 Cloudflare），失败自动重试 3 次（20/40/60s 退避）；再失败回退到规则版日报并照常推送（单条）。
- **目标群**：`engine_config.json` 的 `chat_id`；留空时按群名「信息源引擎」自动查找，找不到回退 `feishu.env` 默认群。
- **产物**：`reports/YYYY-MM-DD-engine.md`；日志 `logs/daily.log`。
- **手动**：

```powershell
python 1AMdata/news/info_engine.py --dry-run   # 只生成
python 1AMdata/news/info_engine.py --push      # 生成并推送
```
